PROMPTBRIDGE — COMPLETED PRODUCT REQUIREMENTS (MVP)
Status: Completed for now; implementation snapshot dated 2026-10-10

Purpose
-------
This document records the product that exists in this repository at the
project's current completion point. It replaces the earlier aspirational
requirements that described unimplemented classifiers, workflows, and
infrastructure as though they were delivered. Source code is authoritative
where implementation and prose differ.

1. Product summary
==================
PromptBridge accepts a natural-language request and returns a structured
prompt that the user can paste into a separate AI system. It does not perform
the requested task itself. The pipeline classifies the request using keyword
rules, detects a likely domain using keyword rules, retrieves prompt
engineering examples from a local knowledge base, reranks the examples, adds
recent session context, and calls Groq for prompt generation.

Intended users include people who want help turning incomplete or loosely
worded requests into clearer prompts for coding, machine learning, research,
creative writing, analysis, general questions, and task planning.

2. Delivered scope
==================
The completed MVP provides:

- A FastAPI service with prompt generation and a compatibility chat route.
- Rule-based intent categories: code, ml, research, creative, analysis, task,
  and question.
- Rule-based domain labels, including Computer Vision, NLP, Data Science,
  Software Engineering, Machine Learning, Agriculture, Cybersecurity,
  Research, and General.
- Dense retrieval with BAAI/bge-small-en-v1.5 through Qdrant local storage or
  a configured Qdrant server.
- Sparse BM25 retrieval, reciprocal-rank fusion, and cross-encoder reranking
  with cross-encoder/ms-marco-MiniLM-L-6-v2; the generation context uses up to
  five reranked examples.
- Groq chat completion using the configured model name in `pipeline.py`
  (currently `openai/gpt-oss-20b`).
- Session conversation history persisted with SQLite; the most recent three
  turns can be added to generation context.
- Three cache layers for embeddings, retrieval results, and generated answers.
  Redis is used when configured and reachable; otherwise a per-process memory
  cache is used.
- Corpus collection utilities for selected prompt engineering websites and
  arXiv PDFs, synthetic example generation, validation, and Qdrant indexing.
- Prometheus metrics and a Docker Compose deployment with Qdrant, Redis,
  Prometheus, and Grafana.
- Mocked API smoke tests in `tests/test_api.py`.

3. User requirements and acceptance status
===========================================
R1 — Accept a natural language requirement. Implemented by POST
`/generate-prompt` with a JSON `query` field and optional `session_id`.

R2 — Reject blank input. Implemented; whitespace-only query returns HTTP 400.
Request-size limits and comprehensive content validation are not implemented.

R3 — Select a prompt style from user intent and estimate domain. Implemented
with deterministic keyword matching in `rag_service/pipeline.py`; it is not a
trained or probabilistic classifier and does not expose confidence scores.

R4 — Add relevant prompt-engineering examples. Implemented using dense and
sparse retrieval, reciprocal-rank fusion, then cross-encoder reranking.
Retrieved source names and abbreviated selected chunks are returned in the
response. Retrieval quality is dependent on the local corpus and is not
guaranteed.

R5 — Generate a reusable prompt while preserving the request. Implemented by
intent-specific system instructions and the Groq chat API. The output is
generated text and is not automatically checked for factual correctness.

R6 — Maintain session context. Implemented through SQLite-backed histories,
session clear/read routes, and a three-turn context window. Session lifecycle,
retention limits, authentication, and tenant isolation are not implemented.

R7 — Expose an API and operational status. Implemented routes are listed in
`README.md`; `/health` is a basic process response and does not verify the
health of Groq, Redis, or Qdrant.

R8 — Support corpus refresh. Implemented by `rag_data_collection/` scripts.
Validation reports quality findings; a non-strict run does not guarantee that
all low-quality items are removed. Rebuilding with `--recreate` replaces the
Qdrant collection.

R9 — Provide service metrics and dashboard configuration. Implemented with
Prometheus exposition and checked-in Prometheus/Grafana configuration.

4. API contract
===============
POST `/generate-prompt` and POST `/chat`

Request:
  {"query": "Create a prompt for debugging a Python API",
   "session_id": "optional-session-id"}

Response fields:
  `query`, `optimized_prompt`, `intent`, `domain`, `sources`, `latency_s`,
  `chunks`, and `cached`. Each returned chunk is abbreviated and may include
  `text`, `source`, `doc_title`, and `rerank_score`.

Other routes:
  GET `/health`
  GET `/session/{session_id}`
  POST `/session/clear` with `{ "session_id": "..." }`
  GET `/cache/stats`
  POST `/cache/flush`
  GET `/metrics`

Interactive OpenAPI documentation is available at `/docs` while the API runs.

5. Quality and operating constraints
=====================================
- The service requires a valid Groq API key for uncached prompt generation.
- Retrieval requires a compatible index generated with the same embedding
  model and collection configuration as the runtime retriever.
- The default data store is local Qdrant. SQLite and local Qdrant files are
  runtime data and should be backed up as needed.
- API keys belong in environment variables or `.env`; `.env` must not be
  committed. The repository's `.env.example` includes placeholders for optional
  data-collection integrations.
- CORS origins are configurable with `CORS_ORIGINS`; its code default is `*`.
- The implementation is a single-process prototype. In-memory caches and
  session pipeline instances are process-local; the session registry does not
  provide multi-worker coordination.
- The application does not provide API authentication, rate limiting, or a
  user-facing web frontend.
- Generated prompts may contain errors or assumptions. Human review remains
  appropriate, particularly for consequential use.

6. Not delivered / deferred
===========================
The following ideas appeared in the original product concept but are not
implemented by this completed MVP: a DistilBERT classifier, independently
served embedding service, MLflow experiment tracking/model registry, model
training or automatic retraining, Airflow orchestration, automated quality
gates and deployment, user feedback/rating collection, regeneration controls,
authentication, rate limiting, formal drift detection, alerting, and
production-scale multi-instance session/cache coordination. Cloudflare R2
upload helpers and environment placeholders exist for ingestion, but R2 is an
optional external integration rather than a required runtime dependency.

7. Completion definition
========================
The project is considered completed for its current scope: the repository
contains the API, retrieval/generation pipeline, data preparation utilities,
local and containerized service configuration, monitoring configuration, and
API smoke tests. This status records a project milestone; it does not claim a
formal production-readiness audit or guaranteed service-level objectives.

For setup and usage see `README.md`. For component interactions see
`system_architecture.md`. For the full implementation and repository guide see
`PROJECT_DETAILS.md`.
